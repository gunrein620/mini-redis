# 5조 MINI-REDIS Project 발표

## 발표 주제

**Mini Redis의 원자적 연산과 PostgreSQL의 행 잠금을 비교해, 선착순 쿠폰 시스템에서 어떤 차이가 나는지 보여주는 발표**

---

## 1. 오프닝

안녕하세요. 저희는 Python으로 직접 구현한 Mini Redis를 활용해서 선착순 쿠폰 발급 시스템을 만들었습니다.

이번 발표에서는 단순히 "Redis가 빠르다"를 보여주는 것이 아니라,

- 단건 요청에서는 얼마나 차이가 나는지
- 동시 요청이 몰리면 어떤 방식이 더 유리한지
- TTL 기반 만료 처리가 실제로 어떻게 동작하는지

이 세 가지를 화면 중심으로 보여드리겠습니다.

---

## 2. 화면 1 - 단건 발급 비교

### 발표 흐름

1. 첫 화면에 진입합니다.
2. `Redis 발급` 버튼을 눌러 처리 시간을 확인합니다.
3. `재고 초기화` 후 `DB 발급` 버튼을 눌러 처리 시간을 확인합니다.
4. 단건 기준으로는 큰 차이가 없다는 점을 설명합니다.

### 발표 대사

먼저 첫 화면입니다.

여기서는 같은 쿠폰 발급 기능을 Redis 방식과 DB 방식으로 각각 실행해볼 수 있습니다.

먼저 Redis 발급을 한 번 눌러보겠습니다. 처리 시간은 짧게 나오지만, 사실 단건 요청에서는 DB도 크게 느리지 않습니다.

이번에는 재고를 다시 초기화하고 DB 발급도 해보겠습니다.

보시는 것처럼 **단건 요청에서는 두 방식의 차이가 아주 극적으로 보이지는 않습니다.**

그 이유는 요청이 1건일 때는 락 경합도 거의 없고, 재고를 차감하는 작업 자체도 크지 않기 때문입니다.

그래서 이 프로젝트의 핵심은 단건 성능이 아니라, **많은 사용자가 동시에 몰리는 순간에도 정확하고 빠르게 처리할 수 있느냐**입니다.

### 강조 포인트

- 단건 비교에서는 체감 차이가 크지 않다.
- 진짜 차이는 **동시성 상황**에서 드러난다.
- 그래서 다음 화면의 1000명 동시 테스트가 핵심이다.

---

## 3. 화면 2 - 1000명 동시 테스트

### 테스트 조건

- 재고를 먼저 **100개로 초기화**
- **1000개의 요청이 각각 독립적으로 동시에 들어오도록 설정**
- Redis 방식과 DB 방식을 **같은 조건**에서 순서대로 비교

### 발표 흐름

1. `1000명 동시 테스트` 버튼을 클릭합니다.
2. 결과 카드에서 Redis와 DB 처리 시간을 비교합니다.
3. Redis가 더 빠른 이유를 동시성 처리 방식 관점에서 설명합니다.

### 발표 대사

저희 Mini Redis는 **단일 스레드 기반의 원자적 `DECR` 연산**을 활용해 선착순 이벤트를 구현했습니다.

트래픽이 아무리 몰려도 레디스 내부에서는 모든 요청이 순차적으로 처리되므로, 정확히 100개의 요청에 대해서만 0 이상의 값을 반환합니다.

이후 **반환값이 음수(-1 등)가 되는 시점부터는 백엔드 쿼리를 실행하지 않고 즉시 에러 응답을 보냄으로써**, DB 부하를 원천 차단하는 '게이트키퍼' 역할을 수행합니다."

### 강조 포인트

- Redis는 **재고 차감 자체가 게이트 역할**을 한다.
- 100개만 성공하고 나머지는 빠르게 차단한다.
- DB는 정확하지만, 대량 동시 요청에서는 잠금 대기 비용이 커진다.

---

## 4. 화면 3 - TTL 유효성 확인 데모

### 발표 흐름

1. TTL 데모 화면으로 이동합니다.
2. `유효 쿠폰 조회`를 눌러 현재 살아 있는 쿠폰 목록을 확인합니다.
3. TTL이 남아 있을 때 `사용하기`를 눌러 사용 가능 여부를 확인합니다.
4. 만료 시간이 지난 뒤 다시 확인해서 사용 불가능 상태를 보여줍니다.

### 발표 대사

세 번째 화면은 쿠폰 TTL 데모입니다.

저희는 쿠폰을 발급할 때 Redis에 쿠폰 코드를 저장하면서 TTL도 함께 설정했습니다.

그래서 이 화면에서는 **현재 살아 있는 쿠폰이 몇 장인지**, 그리고 **각 쿠폰의 남은 시간이 얼마나 되는지**를 실시간으로 확인할 수 있습니다.

먼저 유효 쿠폰 조회를 해보면, Redis 쪽은 남은 TTL 기준으로 쿠폰을 보여주고 DB 쪽은 `expires_at` 기준으로 같은 쿠폰을 보여줍니다.

이 상태에서 TTL이 남아 있을 때 `사용하기`를 누르면, Redis에 아직 키가 살아 있기 때문에 **사용 가능**하다는 응답을 받을 수 있습니다.

그리고 시간이 지나 TTL이 만료되면 Redis에서는 해당 키가 자동으로 사라집니다.

그 이후 다시 확인하면 더 이상 유효한 쿠폰으로 인정되지 않고, **만료된 쿠폰이라 사용 불가능**하다는 결과를 보여줄 수 있습니다.

즉, 이 데모는 **Redis의 TTL이 단순 저장 기능이 아니라, 쿠폰 만료를 자동으로 처리하는 장치**로도 활용될 수 있다는 점을 보여줍니다.

### 강조 포인트

- TTL이 살아 있으면 사용 가능
- TTL이 만료되면 Redis에서 자동 삭제
- 별도 배치 없이도 만료 처리를 자연스럽게 구현 가능

---

## 5. 마무리

정리하면,

- 단건 요청에서는 Redis와 DB의 차이가 아주 크지 않았습니다.
- 하지만 **1000명 동시 요청**처럼 트래픽이 몰리는 상황에서는 Redis의 원자적 `DECR`이 훨씬 유리했습니다.
- 그리고 TTL 기능을 통해 쿠폰의 **유효 시간 관리와 만료 처리**까지 간단하게 구현할 수 있었습니다.

즉, 이번 프로젝트를 통해 저희는 Redis를 단순 캐시가 아니라,

**선착순 제어, 트래픽 차단, 만료 처리까지 담당하는 실시간 이벤트 게이트키퍼**

로 활용할 수 있다는 점을 확인했습니다.

감사합니다.
